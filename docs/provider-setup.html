1. CASParser: prepare portfolio testing

  1. Revoke the exposed old key in your provider dashboard and create a FolioKey-specific replacement.
  2. Store it server-side as FOLIOKEY_CAS_PARSER_API_KEY in the intended Vercel environment. Do not put it in chat, Git, a screenshot or a NEXT_PUBLIC_ variable.
  3. Confirm account credits, rate limits, response schema, statement generation delivery and file retention. The provider's documented SDK offers CAMS/KFintech email requests; that is distinct from universal mobile-only retrieval.
  4. After release review, test one original detailed CAS: preview, masked folios, units/value reconciliation, excluded assets, confirm and identical reimport.

The prior temporary credential window is not extended. Resend's exposed credential also needs revocation even though custom OTP auth has been retired. Supabase remains FolioKey's only sign-in system.

2. Mobile/OTP: confirm eligibility before buying an API

AA uses an explicit consent object and can request mutual-fund information. Mobile discovery is part of that journey; it is not a guarantee of every investment being found. The Government's AA framework description and Sahamati FAQ describe FIUs as regulated entities. Ask the provider to confirm FolioKey's permitted role or an eligible partner arrangement in writing.

We are building FolioKey, an Indian mutual-fund portfolio intelligence product using Supabase authentication. We want consent-based, read-only portfolio retrieval through a mobile/OTP journey, with no trade execution.

Please confirm:
1. Our permitted role, onboarding requirements and any eligible regulated FIU/partner arrangement required for this use case.
2. Actual production MF FIP/RTA coverage, physical versus demat funds, summary/transactions/SIP coverage and account-discovery limitations.
3. Sandbox credentials and non-personal sample payloads for account linking, consent approval, rejection, expiry and revocation.
4. Historical coverage, opening/running units, stable transaction IDs, reversals/corporate actions, pagination, corrections and partial-data flags.
5. Consent purpose, data life, fetch frequency, retention/deletion, residency, encryption, webhook signature/replay verification and idempotency contracts.
6. Setup fee, minimum commitment, monthly/platform charges, per-consent/fetch fees, failure charging, sandbox limits and support/SLA.
7. Commercial processing, storage, display and derived-analytics rights.

We will not scrape private APIs, bypass controls, accept contracts or start billable traffic before review.

This is a draft you may send yourself. It has not been sent to a provider. Do not send customer PANs, phone numbers, CAS documents or API keys with an initial enquiry.

3. Fund data: ask for a coverage sample and rights

Provider marketing does not establish that the package covers Indian mutual funds or that FolioKey may redistribute data. Obtain a dated coverage sample and written rights before integration.

Required for FolioKey:
- Stable Indian MF scheme, ISIN and direct/regular/growth/IDCW identifiers, matched plan families and dated category/benchmark mappings.
- Dated NAV and distribution/corporate-action history, inception/closure/merger metadata and corrections; distinguish price/NAV change from total return.
- Licensed total-return benchmark and category histories with constituents/membership changes, calendars and survivorship handling.
- Dated expense ratios, AUM, risk disclosures and holdings/security weights, including cash/derivative scope and disclosure completeness.
- API/feed schema, identifiers, pagination, rate limits, backfill limits, revision versioning, provenance, freshness and outage behavior.
- Commercial display, storage, export and derived-analytics rights, attribution, user limits and termination/deletion obligations.
- Written pricing, minimum commitment, backfill charges and SLA.

Please provide a non-customer sample and a coverage report. No investment recommendations will be generated from unverified or missing data.

Public AMFI downloads are useful input to the current browser tools. Public accessibility alone does not establish commercial redistribution rights for a full automated data product.

4. Jev: optional after the data foundation

No new AI key is required to use the deterministic guide, ledger, charts or planning tools. If enabling question matching later, securely configure:

FOLIOKEY_ENABLE_JEV_GUIDE=true
FOLIOKEY_JEV_API_KEY=[server-side secret]
FOLIOKEY_JEV_MODEL=[reviewed documented model identifier]

These are configuration names, not real credentials. The new migration adds an independent five-attempt rolling 24-hour guard. The UI requires consent for sending the question to TypeSafe. FolioKey does not automatically send holdings or planning records; model confidence is not financial confidence. A model key does not provide NAV, constituents, tax rules or suitability.

  2. Review the additive planning/guide migration in an approved environment; this work did not apply it to production.
